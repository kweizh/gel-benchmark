# Gel: Delegated Constraints, Multiple Inheritance, and a TypeScript Ingest Classifier

## Background
A hardware fleet team keeps its asset registry in a local **Gel 6** database (the graph-relational database formerly known as EdgeDB). Their compliance rules are expressed entirely as schema-level constraints, and a nightly batch job pushes a JSON manifest into the registry. Records that break a rule must not sink the whole batch: they have to be rejected individually, classified by the rule they broke, and reported.

Your job is to design the schema, migrate it, and build the batch ingest tool.

A local Gel 6 server is installed in this container but is not started automatically: run `bash /usr/local/bin/gel-ensure-server.sh` to bring it up (the helper is idempotent and blocks until the server accepts queries). Its connection settings are already supplied through preconfigured `GEL_*` environment variables — do not change them, and do not point the tool at any other instance. Everything else you need is already installed: the `gel` CLI, Node.js, TypeScript tooling and the `gel` npm client, with `node_modules` already populated. Treat the environment as offline and do not try to download packages.

## Requirements

### 1. Schema and migration
Design the schema for module `default` and apply it through Gel's migration system, so that `dbschema/migrations/` holds the applied migration(s) and the database reports being fully migrated.

The schema must contain exactly these object types, with exactly these pointer names:

- `Region` — required `key: str`. `key` must be unique across all `Region` objects; the violation must report the message `REGION_KEY_DUPLICATE`.
- abstract type `Revisioned` — required `revision: int64` whose minimum allowed value is `1`; the violation must report the message `REVISION_TOO_LOW`.
- abstract type `Taggable` — a **multi** property `tags: str`; every individual tag value must satisfy the shared token rule (below) with a length limit of `12`.
- abstract type `Asset`, which must extend **both** `Revisioned` and `Taggable`, with:
  - required `code: str` — must satisfy the shared token rule with a length limit of `16`, and must be unique **only among objects of the same concrete asset type**. The very same `code` value must remain insertable under a *different* concrete asset type. A same-type duplicate must report the message `CODE_DUPLICATE_IN_KIND`.
  - required `serial: str` — must be unique **across the whole `Asset` hierarchy**, i.e. a value used by one concrete asset type must be rejected for every other concrete asset type too. The violation must report the message `SERIAL_DUPLICATE_GLOBAL`.
  - required single link `region` pointing at `Region`.
  - required `slot: int64`, required `capacity: int64`, required `reserved: int64`.
  - the pair (`region`, `slot`) must be unique **only among objects of the same concrete asset type**; the same (`region`, `slot`) pair must remain insertable under a different concrete asset type. The violation must report the message `SLOT_DUPLICATE_IN_KIND`.
  - `reserved` must never be greater than `capacity`; the violation must report the message `CAPACITY_EXCEEDED`.
- `ServerAsset`, extending `Asset` — required `hostname: str`.
- `StorageAsset`, extending `Asset` — required `volume_gb: int64`.
- `Operator` — required `name: str`, unique across all `Operator` objects, violation message `OPERATOR_NAME_DUPLICATE`; plus a **multi** link `crew` pointing at `Asset` that carries a link property `role: str`. A single `Operator` must never be linked to two assets carrying the same `role` value (two *different* `Operator` objects may each use the same `role`). The violation must report the message `ROLE_DUPLICATE_FOR_OPERATOR`.

The **shared token rule** must be expressed as exactly one user-defined *abstract* constraint in module `default` that accepts a single `int64` parameter and is reused at both sites (`Asset.code` with `16`, `Taggable.tags` with `12`). No other user-defined abstract constraint may exist in module `default`. A value satisfies the rule when it matches the regular expression `^[A-Z][A-Z0-9_]*$` **and** its length is less than or equal to the parameter. A violation must report the message `TOKEN_INVALID(max=16)` for `code` and `TOKEN_INVALID(max=12)` for `tags`.

All of the messages above are the exact, complete error text the database must produce — no prefixes, no suffixes, no punctuation of your own.

### 2. Batch ingest CLI (TypeScript)
Build a re-runnable command-line tool that ingests a JSON manifest and writes a JSON report.

- It must read the manifest, make sure every region key it declares exists, then attempt every asset record against the live database, one record at a time, in strictly ascending `seq` order.
- A record that the database refuses must be recorded as rejected and must leave nothing behind in the database, while every following record is still attempted.
- Records are mapped to concrete types by their `kind` field: `"server"` -> `ServerAsset`, `"storage"` -> `StorageAsset`.
- The tool must be safe to run repeatedly against a database that already holds data: pre-existing rows must be honoured as uniqueness conflicts rather than crashing the run, and re-declaring already existing region keys must not fail.

## Implementation Hints
- Project path: `/home/user/assetreg`
- Command: `bash /home/user/assetreg/run-ingest.sh --input <manifest.json> --report <report.json>`. Both flags are mandatory and may appear in either order. Create `run-ingest.sh` yourself; it may launch whatever runtime you like as long as the TypeScript sources of the tool live under `/home/user/assetreg/src/` and drive the database through the `gel` npm client.
- Manifest format (UTF-8 JSON object):

  ```json
  {
    "regions": ["EU_WEST", "US_EAST"],
    "assets": [
      {
        "seq": 1,
        "kind": "server",
        "code": "ALPHA",
        "serial": "SN-0001",
        "region": "EU_WEST",
        "slot": 1,
        "capacity": 10,
        "reserved": 2,
        "revision": 1,
        "tags": ["WEB"],
        "hostname": "host-1"
      }
    ]
  }
  ```

  `seq` values are unique positive integers but are not necessarily contiguous or pre-sorted. The `assets` array may be empty. `tags` may be absent (treat as no tags). `hostname` and `volume_gb` may be absent; when a record omits the property its concrete type requires, the database itself must be the one to reject it. Every record in any manifest you will be given breaks at most one of the declared rules, and every `region` value used by an asset record also appears in `regions`.
- Report file: a JSON object whose top-level keys are exactly `total`, `inserted`, `rejected`, `results`, `reason_counts` and `schema`.
  - `total` is the number of asset records in the manifest; `inserted` and `rejected` are the counts of each outcome and must sum to `total`.
  - `results` is an array with one entry per asset record, ordered by ascending `seq`, each entry having exactly the keys `seq`, `kind`, `serial`, `status`, `reason`, `error_class`. `status` is `"inserted"` or `"rejected"`. For an inserted record `reason` and `error_class` are both `null`.
  - For a rejected record, `reason` is the constraint error message the database produced — that is, exactly the single-line message text declared for the violated constraint in your schema, with none of the extra diagnostic lines (query excerpt, `Details:`, `Hint:`) that the client appends to the raw error. When the database instead refused the record because a required value was absent, `reason` is the literal string `MISSING_REQUIRED`. `error_class` is `"ConstraintViolationError"` in the first case and `"MissingRequiredError"` in the second.
  - `reason_counts` maps every `reason` string that occurred at least once to how many times it occurred; reasons that never occurred must be absent.
  - `schema` is an object with exactly the keys `abstract_constraints`, `delegated_pointer_constraints` and `delegated_object_constraints`, and every one of its values must be derived from live schema introspection performed during the run — never from a hardcoded literal:
    - `abstract_constraints`: ascending array of the module-qualified names of all abstract constraints defined in module `default`.
    - `delegated_pointer_constraints`: ascending, de-duplicated array of `"<TypeName>.<pointerName>"` strings (type name written without its module prefix) for every constraint attached to a pointer of a module-`default` object type that is marked as delegated.
    - `delegated_object_constraints`: ascending, de-duplicated array of module-`default` object type names (without the module prefix) that carry at least one delegated object-level constraint.
- Exit codes: `0` when nothing was rejected, `2` when at least one record was rejected (the report file must still be written in full), and `1` when a required flag is missing or the manifest cannot be read or parsed (in that case no report file may be written and a diagnostic must go to stderr).
- The last line the tool writes to stdout must be exactly `SUMMARY inserted=<inserted> rejected=<rejected>` with the two integers from the report.
