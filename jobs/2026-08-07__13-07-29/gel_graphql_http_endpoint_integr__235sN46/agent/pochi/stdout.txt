# Gel GraphQL-over-HTTP Gateway with Dual-Protocol Verification ## Background Gel 7 (formerly EdgeDB) can expose a full CRUD GraphQL API over plain HTTP directly from the database, but only once the correct built-in extension has been enabled through a real schema migration. A locally installed Gel 7 server is already present in this environment; once started it listens on `127.0.0.1:5656` (branch `main`). The `gel` CLI and the Python client are pre-installed and pre-configured through environment variables, so no credentials, project linking, or cloud access is required. Start (or restart) the server at any time with the idempotent helper `start-gel-server.sh`, which blocks until the server accepts queries. You must model a small service registry, expose it over Gel's HTTP GraphQL endpoint, and build a Python gateway that talks to that endpoint and cross-checks every result against the same data read over Gel's native binary protocol. **Everything is local. Only `127.0.0.1` may be contacted. No external network access, no package installation, and no additional services are available or permitted — every dependency you need is already installed.** ## Requirements ### 1. Schema and migration Author the schema in `dbschema/default.gel` and bring the database in sync with it through the normal migration workflow, so that `gel migration status` reports the database is up to date and `dbschema/migrations/` contains the applied migration file(s). The database's HTTP GraphQL endpoint must be live at `http://127.0.0.1:5656/branch/main/graphql` after your migration is applied. Module `default` must define exactly these named entities (names are checked literally): * Object type `Team` with required property `name` of type `str` that is unique across all teams, required property `region` of type `str`, a computed multi link `services` holding every `Service` that points at this team through its `owner` link, and a computed single property `service_count` of type `int64` holding how many such services exist. * Object type `Service` with required property `name` of type `str` that is unique across all services, required property `tier` of type `int64`, required property `active` of type `bool`, a required single link `owner` to `Team`, and a computed single property `team_name` of type `str` holding the owning team's name. * An expression alias named `ActiveService` that yields exactly the `Service` objects whose `active` is true. All three must be reachable through the GraphQL endpoint, including `ActiveService` as a top-level GraphQL query field and `service_count`/`team_name`/`services` as selectable fields. ### 2. Seed data Load the fixture at `data/seed.json` into the database so that afterwards the database contains exactly the 3 teams and exactly the 9 services described there, with matching `region`, `tier`, `active` and team ownership. Do not add, drop or alter any other objects. ### 3. The gateway module Create an importable Python module at `gateway.py` in the project root. It must speak GraphQL to `http://127.0.0.1:5656/branch/main/graphql` over plain HTTP and expose exactly the following public names. * `GatewayError` — an `Exception` subclass carrying an attribute `errors` that is a list of error-message strings (empty list when there are none). * `ServiceNotFound` — a subclass of `GatewayError`. * `endpoint_url(branch="main")` — returns the GraphQL URL string for that branch; `endpoint_url()` must return exactly `http://127.0.0.1:5656/branch/main/graphql`. * `execute(query, variables=None, operation_name=None, branch="main")` — sends one GraphQL request and returns a `dict` with exactly the keys `data`, `errors`, `status`. `data` is the response's GraphQL data object or `None` when absent, `errors` is the list of error-message strings (empty list when there are none), `status` is the integer HTTP status code of the response. It must never raise for a GraphQL-level error nor for a non-2xx HTTP response; when the response body is not JSON, `data` must be `None` and `errors` must be a one-element list holding the whitespace-stripped response body. * `last_request()` — returns a `dict` with exactly the keys `url`, `query`, `variables`, `operation_name` describing the most recent GraphQL request the module actually sent (`variables` is `{}` when none were sent, `operation_name` is `None` when none was sent), or `None` if the module has not sent one yet. * `list_services(region=None, min_tier=None, active_only=False, limit=None, offset=0)` — returns a list of dicts, each with exactly the keys `name`, `tier`, `active`, `team`, `region`, ordered by `name` ascending. `team` is the owning team's name and `region` is the owning team's region. `region` restricts results to services whose owning team has that region; `min_tier` keeps services whose `tier` is greater than or equal to it; `active_only=True` keeps only active services; `limit`/`offset` select a window of the ordered, filtered result. Selection, ordering and windowing must be performed by the database, not in Python: the request recorded by `last_request()` must always carry an `order` argument, must carry a `filter` argument whenever any of `region`, `min_tier` or `active_only` narrows the result, must carry a `first` argument whenever `limit` is not `None`, and must carry an `after` argument whenever `offset` is greater than 0. `limit` must be `None` or a positive integer and `offset` must be a non-negative integer; anything else must raise `ValueError` without sending a request. * `fetch_teams()` — returns a list of dicts, each with exactly the keys `team`, `region`, `service_count`, `active_service_count`, `services`, ordered by `team` ascending. `services` is the list of that team's service names ordered ascending, `service_count` is the total number of services owned by the team, `active_service_count` is how many of them are active. * `create_service(name, tier, active, team)` — inserts a new service linked to the existing team with that name, and returns the created record as a dict with exactly the keys `name`, `tier`, `active`, `team`, `region`. The values must travel as GraphQL variables: the request recorded by `last_request()` must expose them under `variables` and its `query` document must not contain the literal `name` value. If the database reports any GraphQL error (for example because no such team exists) it must raise `GatewayError` with a non-empty `errors` list, and nothing may be inserted. * `retire_service(name)` — updates the named service so that `active` becomes false and returns the updated record with the same five keys as `create_service`; raises `ServiceNotFound` when no service has that name. * `delete_service(name)` — deletes the named service and returns the deleted record with the same five keys; raises `ServiceNotFound` when no service has that name. * `verify_parity()` — fetches every service over the HTTP GraphQL endpoint and independently fetches the same services over Gel's native binary protocol, then returns a dict with exactly the keys `http_count`, `binary_count`, `match`, `differences`. `http_count` and `binary_count` are integers, `match` is a bool that is true only when both protocols yield the identical set of service records (name, tier, active, owning team and region), and `differences` is a sorted list of strings that is empty if and only if `match` is true. * `build_report()` — returns a dict with exactly the keys `endpoint`, `teams`, `pages`, `parity`. `endpoint` is `endpoint_url()`. `teams` is the output of `fetch_teams()`. `pages` is a dict with exactly the keys `page_1`, `page_2`, `page_3`, where each value is the list of service names in that page when all services ordered by `name` ascending are split into consecutive pages of size 2 (`page_1` is the first two names, `page_2` the next two, `page_3` the next two). `parity` is the output of `verify_parity()`. ### 4.
