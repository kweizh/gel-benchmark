Bookkeeping fields on `Product` Extend `default::Product` (keep the existing properties and constraints intact) with two required properties that the database maintains on its own: - `revision: int64` — a new product starts at `1`. Every `update` statement that matches the product increases its `revision` by exactly `1`, **even when the statement does not actually change any value**. - `price_history: array<int64>` — a product inserted after your change starts with `[<its price_cents>]`. Every `update` that changes `price_cents` appends the new price to the array; an `update` that leaves `price_cents` at its current value must leave the array untouched. The 8 products that already exist must be backfilled with `revision = 1` and `price_history = []` (do not synthesize history for them). ### 2. `default::AuditEvent` — one append-only row per audited row change Properties: - `action: str`, required, restricted to exactly the values `insert`, `update`, `delete`. - `sku: str`, required. - `old_price_cents: int64`, optional. - `new_price_cents: int64`, optional. - `recorded_at: datetime`, required, defaulting to the time of the statement that created it. - `summary: str`, required, and **always derived by the database from the other properties of the same object when the row is inserted** (a caller-supplied value must never survive). Exact formats: - `action = 'insert'` → `INSERT <sku> price=<new_price_cents>` - `action = 'update'` → `UPDATE <sku> price=<old_price_cents>-><new_price_cents>` - `action = 'delete'` → `DELETE <sku> price=<old_price_cents>` The type is append-only: inserting is allowed (including directly, by hand), but any attempt to `update` or `delete` an `AuditEvent` must fail with an error whose message contains exactly `AuditEvent is append-only`, and must leave the stored rows unchanged. ### 3. `default::AuditBatch` — one row per mutating statement Properties: `kind: str` (required, restricted to exactly `insert`, `update`, `delete`), `row_count: int64` (required), `recorded_at: datetime` (required, defaulting to the time of the statement that created it). Exactly one `AuditBatch` row must be recorded per `insert`/`update`/`delete` statement executed against `Product`, with `kind` naming the statement type and `row_count` holding the number of `Product` objects that statement modified. This includes statements that modified **zero** products (e.g. an `update Product filter ...` whose filter matched nothing): those must still produce exactly one `AuditBatch` row, with `row_count = 0`. ### 4. Required declaration names The audit behaviour must be declared in the schema with exactly these names: On `default::Product`: | name | reacts to | granularity | | --- | --- | --- | | `log_product_insert` | insert | one `AuditEvent` per inserted product | | `log_price_update` | update | one `AuditEvent` per updated product, **only** when `price_cents` actually changed — expressed as the trigger declaration's own condition, so the trigger body does not even run otherwise | | `log_product_delete` | delete | one `AuditEvent` per deleted product | | `batch_insert_stats` | insert | one `AuditBatch` per statement | | `batch_update_stats` | update | one `AuditBatch` per statement | | `batch_delete_stats` | delete | one `AuditBatch` per statement | On `default::AuditEvent`: `forbid_mutation`, reacting to both `update` and `delete`, per row. An `update` of a product that leaves `price_cents` unchanged must therefore produce **no** `AuditEvent` at all (while still bumping `revision` and still producing an `AuditBatch` row). ### 5.
