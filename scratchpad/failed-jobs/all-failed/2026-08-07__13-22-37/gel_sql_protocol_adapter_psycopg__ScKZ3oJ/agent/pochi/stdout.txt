# Dual-protocol reconciliation for a Gel catalog (EdgeQL binary protocol vs. PostgreSQL wire protocol) ## Background A Gel 6 server runs locally inside this container and is already linked to the project at `/home/user/project`. Gel speaks two wire protocols on the very same port: its native binary protocol (used by the Python `gel` client) and a PostgreSQL-compatible protocol (usable by any Postgres driver, e.g. `psycopg`). Both expose the *same* stored data, but through two very different surfaces: EdgeQL object types/links/properties on one side, and plain SQL relations on the other. The data team no longer trusts either surface on its own. Your job is to model a small music catalog in Gel, load a dataset into it over the native protocol, and then build a reconciliation tool that recomputes an agreed-upon set of figures **independently over each protocol** and reports, exactly and machine-readably, wherever the two disagree — plus any drift against a previously captured report. Everything runs locally. The Python `gel` client, `psycopg` (v3), `pytest` and the Gel CLI are already installed; do not download anything and do not rely on any external service. ## Requirements ### 1. Schema Define the following in the Gel module `catalog` (all names are exact and case-sensitive), apply it through Gel's migration system, and leave the migration files in `dbschema/migrations/` with the branch reported as up to date: * abstract type `Asset` with required `title: str` and required `slug: str`; `slug` is unique across all assets. * type `Artist` with required `handle: str` (unique), required `name: str`, required `country: str`, and a multi property `aliases: str`. A `country` value that is not exactly two uppercase ASCII letters must be rejected by the database itself. * type `Album extending Asset` with required `year: int32` and optional `label: str`, and an index on `year`. * type `Track extending Asset` with: * required `duration_ms: int64`, which the database must reject when it is less than 1; * required `royalty_rate: decimal`; * a required single link `album` to `Album`; * a multi property `tags: str`; * a multi link `contributors` to `Artist` carrying two link properties, `role: str` and `share_bp: int64`; * a computed single property `payout_micros: int64` whose value is the integer floor of `duration_ms * royalty_rate`. ### 2. Otherwise the baseline is a previously written report in this same format, and drift is computed over the **`edgeql`** side only: one entry per metric whose value differs (`scope` `metric`, `field` `value`), and one entry per differing row field (`scope` `row`, `id` the slug, `field` the row-object key). A track present in only one of the two reports produces eight entries — one per row-object key — with `null` on the side where it is absent. `drift_count` is the length of this array.
