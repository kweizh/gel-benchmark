# Schema-Enforced Audit Log and Metadata Engine in Gel ## Background `/home/user/auditdb` is an existing **Gel** project (server **6.x**, branch `main`, module `default`) that already contains a small amount of live data: a few `Document` objects (`slug`, `title`, `body`) and `Comment` objects (`body`, plus a required `document` link to a `Document`). Its schema lives in `dbschema/` and its migration history in `dbschema/migrations/`. A compliance review concluded that the application layer cannot be trusted to maintain audit trails or row metadata: different services write to the database, some of them send stale or forged bookkeeping values, and several of them use bulk statements and multi-statement transactions. You must therefore move the whole audit-and-metadata engine **into the database itself**, so that it is impossible for any client to write to `Document` or `Comment` without a correct, tamper-proof trace being produced automatically. Every check is performed by executing **plain EdgeQL statements directly against the instance** — no code of yours is ever called by the checker, and no application-level wrapper, helper function, script, or scheduled job may take part in producing the results described below. ## Requirements ### 1. Row metadata on `Document` and `Comment` Both `Document` and `Comment` must gain three required properties whose values are produced by the database, never by the client: - `version: int64` — `1` immediately after the object is inserted, and exactly one greater than its previous value after **every** successful `update` statement that matches the object, including updates that assign the very same values it already had. - `created_at: datetime` — the timestamp of the statement that inserted the object; it must never change again for the lifetime of the object. - `modified_at: datetime` — equal to `created_at` immediately after the insert, and equal to the timestamp of the most recent `update` statement that matched the object. A client that explicitly supplies `version`, `created_at`, or `modified_at` in an `insert` or an `update` (including values in the far past or future) must have those values silently discarded: the resulting stored values must be exactly the ones described above. Inserts that do not mention these properties must succeed. ### 2. Denormalized parent key on `Comment` `Comment` must gain a required property `document_slug: str` that always mirrors the `slug` of the `Document` the comment currently links to. It must be filled in automatically on insert, follow the comment when an update re-points its `document` link to a different `Document`, and ignore any value a client supplies for it. ### 3. Immutable audit log Add an object type `AuditEntry` in module `default` with these properties: - `action: str` — one of `'insert'`, `'update'`, `'delete'`. - `entity_type: str` — `'Document'` or `'Comment'`. - `entity_id: uuid` — the `id` of the audited object. - `version: int64` — the audited object's `version` as of that statement; for a deletion, the `version` the object had at the moment it was deleted. - `at: datetime` — the timestamp of the statement that caused the mutation, so that **all** audit entries produced by one statement carry exactly the same `at`, and an entry recording an insert or an update carries exactly the `created_at` / `modified_at` value that same statement stored on the object. - `snapshot: json` — a JSON object with exactly the keys `slug`, `title`, `version` for a `Document`, and exactly the keys `body`, `document_slug`, `version` for a `Comment`, holding the audited object's values as of that statement (for a deletion, the values it had when it was deleted). Audit entries must appear purely as a side effect of ordinary `insert`, `update` and `delete` statements run against `Document` and `Comment`: - Exactly one entry per affected object per mutating statement — including statements that mutate many objects at once (e.g. a `for` loop over a set) and statements inside explicit multi-statement transactions. Never two entries for the same object and statement, and never an entry for a statement that only reads. - Audit writes are part of the same transaction as the mutation: if the transaction is rolled back, no audit entry survives. - Deleting a `Document` that still has comments must succeed, must remove those comments, and must record exactly one `'delete'` entry for the `Document` plus exactly one `'delete'` entry for **each** removed `Comment` (with that comment's own `version`, `body` and `document_slug`). - The log is append-only: any `update` or `delete` statement targeting existing `AuditEntry` objects must fail with an error and leave the log byte-for-byte unchanged. ### 4. Preserve the existing data and migration history The `Document` and `Comment` objects that already exist must survive with their `slug`, `title`, `body` and `document` links intact, and must end up with a `version` of at least `1` and with non-empty `created_at` / `modified_at` values (their exact backfilled timestamps do not matter). All schema changes must be recorded as migration(s) under `dbschema/migrations/` and applied to the instance, so that `gel migration status` reports the database up to date and exits `0`. ### 5. Audit trail report Provide `/home/user/auditdb/audit_report.py`, a read-only reporting command. ## Implementation Hints - Project path: `/home/user/auditdb` (schema in `dbschema/`, migrations in `dbschema/migrations/`). Everything is local: the Gel server, the `gel` CLI and the Python `gel` client are already installed, and connection parameters are already exported in the environment, so the CLI and clients connect to branch `main` of the local instance with no extra configuration. - The local Gel server may be stopped when you start; `/usr/local/bin/gel-up` starts it if needed, is idempotent, and returns only once the server accepts queries. - Use exactly the module (`default`), type names (`Document`, `Comment`, `AuditEntry`) and property names (`version`, `created_at`, `modified_at`, `document_slug`, `action`, `entity_type`, `entity_id`, `at`, `snapshot`) given above; do not rename or drop anything that already exists. - Report command: `python3 /home/user/auditdb/audit_report.py --slug <slug>`, runnable from any working directory. It must exit `0` and print to stdout nothing but a single JSON object with exactly these keys: ```json { "slug": string, "document_exists": boolean, "current_version": integer or null, "document_entry_counts": {"insert": integer, "update": integer, "delete": integer}, "document_max_version": integer or null, "comment_entry_counts": {"insert": integer, "update": integer, "delete": integer}, "deleted_comment_bodies": [string] } ``` where, for the requested `<slug>`: `document_exists` and `current_version` describe the `Document` with that `slug` that currently exists (`current_version` is `null` when there is none); the audit entries counted are those with `entity_type = 'Document'` whose snapshot `slug` equals `<slug>` and those with `entity_type = 'Comment'` whose snapshot `document_slug` equals `<slug>`; both count objects always carry all three action keys, using `0` for actions with no entries; `document_max_version` is the largest `version` among the counted `Document` entries, or `null` if there are none; and `deleted_comment_bodies` lists the snapshot `body` of every counted `Comment` entry whose action is `'delete'` (one element per entry) sorted in ascending order. - Running the report must never change any stored data, and it must keep working for a slug that has no data at all as well as for a slug whose `Document` has already been deleted. - If `--slug` is missing, the report must print nothing on stdout and exit with a non-zero status. - The container is memory constrained (~4 GB of RAM, few CPUs) and everything must run locally inside it: keep any data you create small and do not rely on any external or cloud service.
