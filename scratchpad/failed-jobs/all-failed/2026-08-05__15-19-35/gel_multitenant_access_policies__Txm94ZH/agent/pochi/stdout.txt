# Database-enforced multi-tenant isolation (Gel 7.1, Python) ## Background `/home/user/tenantdesk` holds a small support-ticket service backed by a **Gel 7.1** instance that runs inside this container. Today the CLI decides what a caller may see by filtering in Python and by trusting the tenant name the caller passes in, so any new query path — or anyone who simply opens their own connection to the database — can read and rewrite another tenant's tickets. Rebuild it so that tenant isolation is enforced by the database for every connection, and expose a small CLI that runs each command under a per-invocation caller identity. ## The data model Everything lives in module `default`, declared in `/home/user/tenantdesk/dbschema/default.gel`. These names are part of the contract and are queried literally by the graders: - `Tenant` — `slug` (unique) and `name`. - `Actor` — `email` (unique), a link `tenant` to `Tenant`, and `role`, one of `admin`, `agent`, `readonly`. - `Ticket` — `ref`, `subject`, `status` (one of `open`, `pending`, `closed`) and a link `tenant` to `Tenant`. - `current_actor_email` — a session-level variable of type `str` in module `default` that a client sets on its own connection to declare who it is; it carries the `email` of an `Actor`. This is the only identity input the database accepts, and any client may set it to any value it likes. `Ticket.ref` must be unique within a tenant, and two different tenants must be able to use the same `ref` at the same time. ## Isolation rules Let the caller's identity be the `Actor` whose `email` equals `current_actor_email`, with tenant T and role R. All of the following must hold on **every** connection to the database, including connections that never run any of your code and that supply arbitrary values for `current_actor_email`: 1. Tickets belonging to any tenant other than T are invisible: they never show up in query results, counts or aggregates. 2. When `current_actor_email` is unset, or holds a value matching no `Actor`, no `Ticket` is visible and no `Ticket` can be created, changed or removed. 3. A `Ticket` may be created only when R is `admin` or `agent` and the new ticket's `tenant` is T. 4. A `Ticket` may be changed only when R is `admin` or `agent` and the ticket belongs to T. No identity, whatever its role, may ever cause an existing ticket's `tenant` to end up pointing at a different `Tenant`. 5. A `Ticket` may be removed only when R is `admin` and the ticket belongs to T. 6. `Tenant` and `Actor` objects must stay readable on every connection, whatever `current_actor_email` is set to. ## The CLI Command: `python3 app.py <subcommand> [options]`, run with `/home/user/tenantdesk` as the working directory. Every subcommand except `load-seed` takes a required `--actor <email>`, which is the identity the whole command runs under. On success: exit code 0, and stdout containing exactly one JSON document and nothing else. On failure: stdout empty, and stderr containing exactly one line: - exit 4, `error: unknown-actor` — `--actor` matches no `Actor`. - exit 3, `error: denied` — the database refuses the operation, or the ticket named by `--ref` is not visible to the identity. A ticket that belongs to another tenant and a `ref` that exists nowhere must be indistinguishable. - exit 5, `error: conflict` — `create-ticket` was given a `ref` that the identity's own tenant already uses. - exit 2 — malformed invocation (missing or unknown options, or a `--status` outside the three allowed values). Subcommands, with the JSON each must print (every object carries exactly the listed keys): - `whoami --actor <email>` → `{"actor": <email>, "tenant": <slug>, "role": <role>, "visible_tickets": <int>}`, where `visible_tickets` is how many tickets this identity can see. - `list-tickets --actor <email>` → a JSON array of `{"ref": <ref>, "subject": <subject>, "status": <status>, "tenant": <slug>}`, sorted by `ref` in ascending lexicographic order. - `create-ticket --actor <email> --tenant <slug> --ref <ref> --subject <text>` → the created ticket as that same four-key object; a new ticket's status is `open`. `--tenant` comes from the caller and must not be trusted: when it names anything other than the identity's own tenant, the command fails with exit 3. - `update-ticket --actor <email> --ref <ref> [--subject <text>] [--status <status>] [--tenant <slug>]` → the ticket as that same four-key object after the change; at least one of the three optional values must be supplied. `--tenant` asks for the ticket to be moved to that tenant and must fail with exit 3 whenever it names a tenant other than the ticket's current one. - `delete-ticket --actor <email> --ref <ref>` → `{"ref": <ref>, "deleted": true}`. - `load-seed --file <path>` (no `--actor`) → `{"tenants": <int>, "actors": <int>, "tickets": <int>}`, each value being the number of entries from the file that exist in the database when the command finishes. Two further behaviours are graded: - **Concurrent creation.** When several `create-ticket` processes race for the same tenant and `ref`, exactly one must exit 0 and every other one must exit 5 with `error: conflict`. Transient database-level conflicts must be absorbed internally: they may never reach stdout or stderr, and may never produce any other exit code. - **Repeatable loading.** `load-seed` must be safe to run any number of times: it always exits 0, never creates duplicates, and leaves every field equal to the file's contents. ## Implementation hints - Project path: `/home/user/tenantdesk`.
