# Gel: a reusable shipping-pricing domain built from user-defined EdgeQL functions ## Background `/home/user/functions-lab` is an initialized **Gel 6.11** project (branch `main`) belonging to a parcel-shipping back office. Today it only knows about carriers: module `default` contains a single `Carrier` type and the instance already holds two carrier rows plus one applied migration. Every rule about how a parcel is weighed and priced still lives in spreadsheets, and the team wants those rules to live *inside the database* so that every client speaks the same numbers. Your job is to build that domain layer and a small reporting command. All of it must be done through the `gel` CLI — no Python or TypeScript client code, no other database. The CLI in this container is already configured to reach the local instance from any working directory. ## Requirements ### 1. A `logistics` module of custom primitives Add a schema module named `logistics` containing exactly these primitives: - `logistics::shipping_tier` — an enumerated scalar with the labels `Ground`, `Express`, `Overnight`, declared in that order. - `logistics::sku_code` — a scalar over `std::str` that only accepts values matching the regular expression `^SKU-[0-9]{4}$`. A rejected value must fail with the error message `sku must match SKU-0000`. - `logistics::multiple_of` — a **reusable (abstract) constraint** taking one `std::int64` parameter named `step`, satisfied only when the constrained value is an exact multiple of `step`. Its error-message template must be exactly `weight must be a multiple of {step} grams`. - `logistics::packable_grams` — a scalar over `std::int64` carrying two constraints: a minimum value of `50` whose error message must be exactly `weight must be at least 50 grams`, and `logistics::multiple_of` with `step` = `50` (so a violation reports `weight must be a multiple of 50 grams`). ### 2. Seven user-defined functions in module `logistics` All of them are pure EdgeQL. Parameter names, parameter kinds, types and declared volatility are part of the contract and are inspected. Tier constants: | tier | dimensional factor | floor grams | rate (cents per 100 chargeable grams) | |------|--------------------|-------------|----------------------------------------| | `Ground` | 100% | 500 | 4 | | `Express` | 125% | 1000 | 9 | | `Overnight` | 150% | 2000 | 15 | 1. `logistics::billable_grams(grams: std::int64, tier: logistics::shipping_tier) -> std::int64`, volatility `Immutable`. Returns the chargeable weight: take `grams` × the tier's dimensional factor, round **up** to the next whole gram, then return the larger of that number and the tier's floor grams. 2. `logistics::billable_grams(grams: std::int64) -> std::int64`, volatility `Immutable` — a second function of the same name, one positional parameter also named `grams`, returning the same value the two-parameter function returns for the `Ground` tier. Exactly two functions named `logistics::billable_grams` must exist. 3. `logistics::quote_cents(grams: std::int64, tier: logistics::shipping_tier, insured: std::bool) -> std::int64`, volatility `Immutable`. `insured` must be a **named-only** parameter that defaults to `false`; `grams` and `tier` are positional. The price is the chargeable weight for that tier × the tier's rate ÷ 100, rounded **down** to a whole cent; when `insured` is true add a flat `250` cents afterwards. 4. `logistics::batch_total_cents(quotes: std::int64) -> std::int64`, volatility `Immutable`, where `quotes` is a **variadic** parameter. Returns the sum of all the cent amounts it was given, and `0` when it is called with no arguments at all. 5. `logistics::heaviest_grams(parcels: array<std::int64>) -> std::int64`, volatility `Immutable`. Returns the largest element of the array; for an empty array it must return an empty set rather than a number or an error (its return type modifier is therefore optional). 6. `logistics::delivery_note(tier: logistics::shipping_tier, hint: std::str) -> std::str`, volatility `Immutable`. `hint` is positional but must be declared **optional**, so that passing an empty set still calls the function. The result is the tier label lower-cased, then `/`, then the hint — or the literal `default` in place of the hint when the hint is an empty set. Examples: `('Overnight', 'fragile')` yields `overnight/fragile`; `('Express', <empty set>)` yields `express/default`. 7. `logistics::tariff_version() -> std::str` — no parameters, returns the constant `2026.02`, and its volatility **as recorded in the schema** must be `Stable`. ### 3. Domain types in module `default` Keep the existing `Carrier` type and its two rows exactly as they are, then add: - `Parcel` with: required `sku` of type `logistics::sku_code` (unique across parcels); required `weight_grams` of type `logistics::packable_grams`; required `tier` of type `logistics::shipping_tier`; required `insured` of type `std::bool` defaulting to `false`; optional single `handling_hint` of type `std::str`; a required single link `carrier` to `Carrier`; and three computed properties whose values come from the functions above: `chargeable_grams` (the parcel's chargeable weight for its own tier), `price_cents` (the parcel's price for its own tier and insurance flag) and `note` (its delivery note built from its own tier and handling hint). - `Shipment` with: required `code` of type `std::str` (unique); a `multi` link `parcels` to `Parcel`; a computed `total_quote_cents` equal to the sum of its parcels' `price_cents` (`0` when it has no parcels); and a computed `heaviest_parcel_grams` produced by `logistics::heaviest_grams` from its parcels' `weight_grams` (an empty set when it has no parcels). ### 4. Load the seed data `/home/user/functions-lab/seed/data.json` describes four parcels and two shipments. Every one of them must exist in the database exactly as described (a `null` hint means the parcel has no `handling_hint`; `carrier` names an existing `Carrier`; a shipment lists the SKUs it contains). ### 5. The reporting command Write `/home/user/functions-lab/quote.sh`, runnable as `bash /home/user/functions-lab/quote.sh <args>` from **any** working directory, in two modes. **Mode A — `--shipment <code>`.** Print exactly one JSON object on stdout and exit `0`. Top-level keys, in this order: `shipment`, `tariff_version`, `parcel_count`, `parcels`, `heaviest_parcel_grams`, `total_quote_cents`, `batch_total_cents`. - `tariff_version` is whatever `logistics::tariff_version()` returns. - `parcels` is an array of the shipment's parcels sorted by `sku` ascending; each entry has exactly the keys `sku`, `tier`, `weight_grams`, `chargeable_grams`, `price_cents`, `note` in that order, where `tier` is the stored enum label (e.g. `Express`) and the last three are the parcel's computed values. - `heaviest_parcel_grams` is the shipment's computed heaviest weight, or JSON `null` when the shipment has no parcels. - `total_quote_cents` is the shipment's computed total. - `batch_total_cents` is what `logistics::batch_total_cents` returns when each parcel's `price_cents` is handed to it as a separate argument. - All numeric fields must be JSON numbers, and stdout must contain nothing but that one JSON object. **Mode B — `--introspect`.** Print exactly one JSON object on stdout and exit `0`, read live out of the schema catalog (no hand-written copies of your SDL), with top-level keys in this order: `functions`, `scalar_types`, `abstract_constraints`. - `functions`: every function declared in module `logistics`, sorted by name ascending and then by parameter count ascending. Each entry has exactly the keys `name`, `volatility`, `return_type`, `return_typemod`, `params` in that order; `name` and `return_type` are fully qualified as the catalog stores them. `params` is ordered as declared, and each parameter object has exactly the keys `name`, `kind`, `typemod`, `type` in that order, taken verbatim from the catalog — note the catalog records a variadic parameter's type as an array of its element type. - `scalar_types`: every scalar type declared in module `logistics`, sorted by name ascending. Each entry has exactly the keys `name`, `base`, `enum_values`, `constraint_errmessages` in that order: `base` is the name of its immediate supertype as stored in the catalog, `enum_values` is the array of enum labels or JSON `null` for non-enums, and `constraint_errmessages` is an object mapping each of its constraints' fully-qualified names to the error-message **template** stored for that constraint (an empty object when it has no constraints). - `abstract_constraints`: every abstract constraint declared in module `logistics`, sorted by name ascending, each with exactly the keys `name`, `errmessage`, `param_names` in that order, where `param_names` lists its declared parameter names in order, excluding the implicit `__subject__` parameter. **Both modes.** If `--shipment` names a shipment that does not exist, print exactly `{"error": "unknown shipment", "shipment": "<code>"}` on stdout and exit `3`. If the arguments are missing or unrecognised, write nothing to stdout and exit `2`. ## Implementation Hints - Project path: `/home/user/functions-lab`; its schema lives under `dbschema/` and the report command must be `/home/user/functions-lab/quote.sh`. - The local Gel instance is already running; the helper `gel-start` on `PATH` brings it back up idempotently if it is ever down. - The instance rejects schema changes made outside the migration flow, and the project's migration history must be in sync with the schema files when you are done. - Do not modify or delete the existing `Carrier` type, its two rows, or the migration that created them. - The three constraint error messages quoted above are compared verbatim against what the server reports when data is rejected. - Nothing in this task requires network access.
