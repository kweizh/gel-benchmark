# Transactional Catalog Ingest Pipeline on Gel (TypeScript)

## Background
A local **Gel 6** server is installed in this container (start it with `/usr/local/bin/start-gel.sh`) and a Node.js project skeleton is waiting at `/home/user/catalog-ingest`. The project has no schema and no application code yet.

The merchandising team needs a *catalog sync* tool: vendors periodically hand over one JSON file describing a whole batch of products (with their vendor, their tags and their variants). The tool must apply that whole batch to Gel **atomically** — either the entire batch lands or nothing does — and must print a machine-readable summary of what changed, plus database-wide totals, so the sync can be monitored.

Work **offline**: everything you need (`gel` CLI, the `gel` npm client, `tsx`, `typescript`, `@types/node`) is already installed in `/home/user/catalog-ingest/node_modules` and on `PATH`. Do not install anything and do not depend on any remote service — the whole task runs against the local database.

## Requirements

### 1. Data model
Design and apply a Gel schema in module `default` through Gel's migration system (schema source in `dbschema/`, at least one migration file in `dbschema/migrations/`, and `gel migration status` must report that the database is up to date).

The schema must contain exactly these object types, property names, link names and uniqueness rules (the verifier reads the database directly, so names matter):

- `Vendor` — `code: str` (unique across all vendors), `name: str`.
- `Tag` — `label: str` (unique across all tags).
- `Product` — `sku: str` (unique across all products), `title: str`, `price_cents: int64`, `revision: int64`, a required single link `vendor` to `Vendor`, and a `multi` link `tags` to `Tag`.
- `Variant` — a required single link `product` to `Product`, `code: str`, `label: str`, `stock: int64`; `code` must be unique **per product** (two different products may both have a variant `"S"`, one product may not have two variants `"S"`).
- `SyncSource` — `code: str` (unique), `revision: int64`.

All of the listed properties are required. `Product.tags` may be empty and a product may have zero variants.

### 2. The ingest command
Implement the tool in `/home/user/catalog-ingest/src/ingest.ts` (TypeScript, using the `gel` npm client with EdgeQL query text and query parameters; the `@gel/generate` query builder is not available offline). It is invoked from the project root as:

```
npx tsx src/ingest.ts --input <path-to-payload.json>
```

Input payload format:

```json
{
  "source": "vendor_a",
  "revision": 7,
  "products": [
    {
      "sku": "SKU0001",
      "title": "Cafetière",
      "price_cents": 1999,
      "vendor": { "code": "acme", "name": "Acme Inc." },
      "tags": ["kitchen", "café", "kitchen"],
      "variants": [ { "code": "S", "label": "Small", "stock": 3 } ]
    }
  ]
}
```

`tags` and `variants` are optional and default to an empty array. `tags` may contain duplicates, and the same tag label or vendor code may be repeated across many products of the same batch; that is legal input and must never fail.

### 3. Write semantics
Applying a batch must have exactly this effect on the database:

- Vendors are matched by `code`: created if absent, otherwise their `name` is set to the payload value.
- Tags are matched by `label`: created if absent, reused otherwise. `Tag` objects are **never** deleted.
- Products are matched by `sku`: created if absent, otherwise `title`, `price_cents`, `vendor` and `tags` are overwritten with the payload values. After the batch, a product's tag set must be exactly the deduplicated tag list from the payload (tags that are no longer listed are unlinked, but their `Tag` object survives). `Product.revision` is set to the batch `revision`.
- Variants are matched by (`product`, `code`): created if absent, otherwise `label` and `stock` are overwritten. Variants stored for a product that are **not** in that product's payload variant list are deleted.
- Products that are not mentioned in the batch are left untouched.
- `SyncSource` is matched by `source`; after a successful batch its `revision` equals the batch `revision`.
- If a vendor code appears more than once in one batch with different names, the last occurrence in `products` order wins.

### 4. Atomicity and staleness
- The whole batch is applied in a single transaction: if anything is rejected, the database must be **byte-for-byte unchanged** — no partially written product, vendor, tag, variant or source revision.
- A batch whose `revision` is less than or equal to the `revision` already stored for its `source` must be rejected (this is how replays are suppressed). A batch for a source that has never been seen is always accepted (subject to validation).
- Concurrent invocations for *different* sources must all succeed even when they create the same tag labels or the same vendor code at the same time.

### 5. Output contract
`stdout` must contain **exactly one JSON object and nothing else** (no banners, no progress lines — anything else you want to log goes to `stderr`).

On success the process exits with code `0` and prints:

```json
{
  "ok": true,
  "source": "vendor_a",
  "revision": 7,
  "counts": {
    "products_created": 0,
    "products_updated": 0,
    "vendors_created": 0,
    "vendors_updated": 0,
    "tags_created": 0,
    "variants_created": 0,
    "variants_updated": 0,
    "variants_removed": 0
  },
  "products": [
    {
      "sku": "SKU0001",
      "title": "Cafetière",
      "price_cents": 1999,
      "vendor_code": "acme",
      "tags": ["café", "kitchen"],
      "variants": [ { "code": "S", "label": "Small", "stock": 3 } ],
      "created": true
    }
  ],
  "totals": {
    "products_in_db": 1,
    "variants_in_db": 1,
    "tags_in_db": 2,
    "vendors_in_db": 1,
    "stock_total": 3
  }
}
```

The object must have exactly the keys shown, at every level. Semantics:

- `counts.*` describe this batch only, comparing against the database state as it was **before** this run: `*_created` counts entities that did not exist before, `products_updated`/`variants_updated` count entities that did exist before (whether or not any value actually changed), `vendors_updated` counts vendor codes that existed before **and** whose stored `name` differs from the payload name, `variants_removed` counts stored variants deleted because the payload no longer lists them. Every counter is a number.
- `products` contains one entry per product of the batch, sorted by `sku` ascending in Unicode code point order. `tags` is the deduplicated tag list sorted ascending in Unicode code point order (i.e. the ordering produced by comparing JavaScript strings with `<`, *not* database collation order). `variants` is sorted by `code` ascending in the same order. `created` is `true` only if the product did not exist before this run. Strings must round-trip exactly as given, without any Unicode normalisation.
- `totals.*` describe the **whole database** after the batch (including rows written by earlier, unrelated batches): `stock_total` is the sum of `stock` over every stored variant, `0` when there is none.

On failure the process exits with code `1`, the database is unchanged, and it prints:

```json
{ "ok": false, "error_code": "INVALID_PAYLOAD", "message": "..." }
```

`message` is any non-empty string. `error_code` is exactly one of:

- `IO_ERROR` — `--input` was not given, or the file is missing, unreadable, or not valid JSON.
- `INVALID_PAYLOAD` — the payload violates the rules below.
- `STALE_REVISION` — the batch revision is not greater than the revision already stored for that source.

Payload validation (any violation ⇒ `INVALID_PAYLOAD`, and it takes precedence over the staleness check):

- the document is not an object; `source` is not a non-empty string; `revision` is not an integer ≥ 1; `products` is missing, is not an array, or is empty;
- a product's `sku` or `title` is not a non-empty string; two products in the batch share a `sku`;
- `price_cents` is not an integer ≥ 0;
- `vendor` is not an object whose `code` and `name` are both non-empty strings;
- `tags` is present but is not an array of non-empty strings;
- `variants` is present but is not an array; a variant's `code` or `label` is not a non-empty string, or its `stock` is not an integer ≥ 0; two variants of the same product share a `code`.
