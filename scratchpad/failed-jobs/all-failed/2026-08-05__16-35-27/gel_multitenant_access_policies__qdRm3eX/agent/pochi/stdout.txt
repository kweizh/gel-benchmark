# Database-enforced multi-tenant isolation (Gel 7.1, Python) ## Background `/home/user/tenantdesk` holds a small support-ticket service backed by a **Gel 7.1** instance that runs inside this container. Today the CLI decides what a caller may see by filtering in Python and by trusting the tenant name the caller passes in, so any new query path — or anyone who simply opens their own connection to the database — can read and rewrite another tenant's tickets. Rebuild it so that tenant isolation is enforced by the database for every connection, and expose a small CLI that runs each command under a per-invocation caller identity. ## The data model Everything lives in module `default`, declared in `/home/user/tenantdesk/dbschema/default.gel`. These names are part of the contract and are queried literally by the graders: - `Tenant` — `slug` (unique) and `name`. - `Actor` — `email` (unique), a link `tenant` to `Tenant`, and `role`, one of `admin`, `agent`, `readonly`. - `Ticket` — `ref`, `subject`, `status` (one of `open`, `pending`, `closed`) and a link `tenant` to `Tenant`. - `current_actor_email` — a session-level variable of type `str` in module `default` that a client sets on its own connection to declare who it is; it carries the `email` of an `Actor`. This is the only identity input the database accepts, and any client may set it to any value it likes. `Ticket.ref` must be unique within a tenant, and two different tenants must be able to use the same `ref` at the same time. ## Isolation rules Let the caller's identity be the `Actor` whose `email` equals `current_actor_email`, with tenant T and role R. All of the following must hold on **every** connection to the database, including connections that never run any of your code and that supply arbitrary values for `current_actor_email`: 1. Tickets belonging to any tenant other than T are invisible: they never show up in query results, counts or aggregates. 2. When `current_actor_email` is unset, or holds a value matching no `Actor`, no `Ticket` is visible and no `Ticket` can be created, changed or removed. 3. A `Ticket` may be created only when R is `admin` or `agent` and the new ticket's `tenant` is T. 4. A `Ticket` may be changed only when R is `admin` or `agent` and the ticket belongs to T.
